# Release and distribution

Establish a versioned release and download path so operators can install nano-llm without cloning the repository or compiling Rust. A release should be created from an explicit semantic-version tag only after the existing release-qualification checks pass. Development builds and pull-request artifacts should remain clearly separate from supported releases, and a failed platform build must prevent publication rather than producing a partial release.

CI should apply the release checks at progressively stronger integration points without treating every code change as a stable release. Pull requests targeting `main` should build and test all release artifacts but publish nothing. Merges to `main` should repeat those checks and may publish an explicitly mutable development image such as `edge` or `main`, provided it cannot be mistaken for a supported version. Only an explicit semantic-version tag or approved release action should publish immutable versioned container images, GitHub Release binaries, checksums, and release notes. Automated version selection and changelog generation may be designed separately if the project later adopts a tool such as Release Please or semantic-release.

Publish a multi-architecture runtime image to GitHub Container Registry as `ghcr.io/ameb8/nano-llm`. Each release should provide an immutable version tag, such as `0.1.0`, alongside intentionally managed convenience tags such as `0.1` and `latest`. The manifest should include both `linux/amd64` and `linux/arm64`, retain the current scratch filesystem and non-root runtime user, and record standard OCI source, revision, version, and license metadata. CI should start the published image with a mounted configuration and verify `/health` before promoting the convenience tags.

Attach the statically linked Linux `x86_64` and `aarch64` executables to the corresponding GitHub Release. Artifact names should include the project, version, operating system, and architecture so downloads remain understandable outside GitHub. Publish a SHA-256 checksum file covering every artifact, verify those checksums before upload, and include concise release notes describing compatibility or configuration changes. Signing or build provenance can be added later, but the workflow should leave a clean seam for them rather than making mutable artifacts part of the release contract.

Provide a copy-and-paste quickstart for both distribution paths. The container example should begin with `docker pull`, use the exact secret variables referenced by the example configuration, mount that file read-only, expose port 4000, and finish with a health check and sample authenticated request. The binary example should show downloading the correct architecture, verifying its checksum, making it executable, validating the configuration, and starting the gateway. A small `.env.example` and a minimal single-provider configuration would make the first run clearer than the broader fallback example; a Compose file may be added if it materially reduces the setup rather than duplicating one short `docker run` command.

An installer script is optional once stable binaries exist. If added, it should be a thin convenience layer that detects only supported Linux architectures, downloads a pinned version over HTTPS, verifies the published checksum before installation, and accepts an explicit destination. It must not silently modify shell profiles, create services, or fetch `latest` when the caller requested a particular version.

The release workflow should be idempotent and use least-privilege GitHub permissions. Re-running a tag may repair an interrupted workflow only when the already-published files are byte-for-byte identical; changing an existing version requires a new release. Documentation should state the supported platforms, the plain-HTTP listener boundary, the external health-probe expectation for the scratch image, and the fact that users must supply their own provider and gateway secrets.
